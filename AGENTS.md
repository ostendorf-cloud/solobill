# solobill

Accounting for a sole trader. The design lives in `docs/concepts/solobill.md`.

The global baseline already applies here and is not repeated below.

## Layout

- `cmd/solobill` wires the service: `internal/config` loads and validates the environment,
  `main.go` builds the database connection, the session store, the local and (optional) OIDC
  authenticators, and `internal/httpapi`'s handler, then runs it through govue's `httpserver` with
  graceful shutdown. `embed.go` embeds `dist/` (the built SPA, written by `task web:build`).
  `dist/` sits under `cmd/` rather than `internal/` because `go:embed` resolves relative to the
  file holding the directive.
- `docs/concepts/solobill.md` is the agreed design this issue's plan implements in steps.
- `db/migrations/` holds the dbmate migrations: `tenants`, `accounts`, `invites`, `customers`,
  `catalogue_items`, `documents`, `document_lines` and `document_numbers`, with the row level
  security policies that are the actual multi-tenancy guarantee. `documents` and `document_lines`
  also carry a `BEFORE UPDATE OR DELETE` trigger each, enforcing that an issued document and its
  lines are never mutated again; `document_numbers` is the per-tenant, per-type, per-year gapless
  counter a document's own number is allocated from, inside the issuing transaction. Every
  migration carries its own reasoning as SQL comments; read those before changing a table, a
  policy or a trigger.
- `internal/money/` is the pure calculation package behind a document's own figures: line totals,
  a line's and a document's own discount, VAT computed once per rate, all per
  `docs/concepts/solobill.md`'s Rounding section and all in exact rational arithmetic
  (`math/big.Rat`), never a float. No database, no clock, no I/O; `internal/storage/postgres` and
  a later rendering step are its only callers.
- `internal/storage/` defines the domain types (`Tenant`, `Account`, `Invite`, `Customer`,
  `CatalogueItem`, `Document`, `DocumentLine`) and the repository interfaces the layers above
  call: `TenantRepository`, `AccountRepository`, `InviteRepository`, `CustomerRepository`,
  `CatalogueItemRepository`, `DocumentRepository`, `DocumentNumberRepository`, and
  `TenantScope.WithTenant`, the one way a tenant-scoped query is allowed to run. Nothing here
  imports pgx or the generated sqlc code.
- `internal/storage/postgres/` is the only implementation, wiring sqlc-generated queries
  (`internal/storage/postgres/sqlcgen`, generated by `task generate:sqlc`, committed, never hand
  edited) into the repository interfaces. `internal/storage/postgres/queries/` holds the `.sql`
  sqlc reads; `sqlc.yaml` at the repository root points sqlc at those queries and at
  `db/migrations` as its schema, parsed statically, no database needed.
- `internal/auth/` is the business logic behind both login paths: an OIDC login against Keycloak
  through govue's `oidc` package, and a local account path (password plus TOTP) behind the same
  `Identity` shape, so a later SaaS self-signup does not need a second auth model. It also holds
  `InviteManager` (creating and redeeming an invite token, enrolling the TOTP secret in the same
  step) and the TOTP helpers. Nothing here is an HTTP handler, except the two govue already hands
  back as `http.Handler` values. See its package doc for the admission-gate decisions it makes
  for OIDC.
- `internal/httpapi/` builds the HTTP server: health and metrics endpoints, the local login,
  logout, "who am I" and invite routes, the OIDC routes when `internal/auth`'s OIDC path is
  configured, and the SPA fallback that serves the embedded Vue build for everything else. See
  its package doc for the middleware chain shape and how a login or invite-accept request
  resolves its tenant.
- `internal/config/` loads solobill's configuration from the environment once, at startup, and
  validates it fully before anything listens. Every secret follows the `_FILE`-suffix convention
  of govue's `envconf.Loader.SecretOrFile` and `RequiredSecretOrFile`, not the narrower
  `envconf.Loader.Secret`; see its package doc.
- `Dockerfile` and `docker-compose.yaml` are the local `docker compose up --build` path: a
  multi-stage build (Vue, then Go with the build embedded, then a distroless runtime) behind a
  Postgres that runs with two separate roles, a superuser used only to apply `db/migrations` and
  a restricted `NOSUPERUSER NOBYPASSRLS` role `cmd/solobill` actually connects as, so the row
  level security guarantee above still holds under compose. The full reasoning is a comment on
  `docker-compose.yaml`'s `postgres` service, not repeated here.
- `charts/solobill/` is the real deployment: a Helm chart with no Postgres subchart, since
  Postgres already runs in the cluster it installs into. It takes a database connection URL,
  user and password as configuration, and documents loudly, since it has no way to enforce it,
  that the configured role must be `NOSUPERUSER NOBYPASSRLS` for the row level security
  guarantee above to mean anything. See `charts/solobill/README.md` for the full reasoning.
- `web/` is the Vue SPA on govue: a login view, an authenticated home view that proves the
  session and CSRF token contract end to end (`GET /api/v1/me`, then a CSRF-protected
  `POST /api/v1/auth/logout`), and an invite-accept view. `web/src/theme/` holds the generated
  brand theme (seed colours in `seed.json`, output in `solobill.css`, both regenerated through
  govue's own theme generator, never hand authored) and `web/src/i18n/locales/` the German and
  English strings every view renders through. This is still a shell: no accounting feature, no
  navigation beyond these three views, by the issue's own plan.

## A build needs the frontend first

`cmd/solobill` cannot compile against an empty `dist/`, because `go:embed` fails when its
pattern matches no file at all. `dist/` is gitignored, generated by `task web:build`.

`task build` and `task test:go` both declare that dependency, so running either one through Task
always populates the frontend first. A bare `go build ./cmd/solobill` or `go test ./cmd/...`
outside Task fails on a fresh checkout for that reason; run `task build` or `task test:go`
instead, or `task web:build` once by hand before reaching for the Go toolchain directly.

## govue's two halves move together

govue releases a Go module and a Vue package under one tag. `go.mod`'s
`require github.com/ostendorf-cloud/govue` and `web/package.json`'s
`@ostendorf-cloud/govue` pnpm git dependency must always name the same tag: a mismatch
means this repository takes half of a govue release and not the other half, silently.
`task check:govue-version` (`internal/depsync`) enforces this: it asks `go list -m` for
the version go.mod actually resolves to, the same resolution `go build` itself uses, and
pulls the tag out of `web/package.json`'s `ostendorf-cloud/govue#<tag>&path:/web`
specifier, then fails naming both versions and both files when they differ.
`web/pnpm-lock.yaml` is not checked separately: its own specifier field already has to
match `web/package.json`'s for `pnpm install --frozen-lockfile` to pass, and its resolved
entry pins a commit hash, not a tag, so it cannot be compared to a version directly.

## Verify before committing

```sh
task check
```

`task --list` shows the individual targets, including the small ones `task check` aggregates.

`task check` never touches a database: `generate:check` (sqlc's output is up to date) parses
`db/migrations` statically, with no connection. The row level security isolation test and
everything else that needs a real Postgres is `task test:integration` instead, deliberately left
out of `check`:

```sh
dbmate up                 # applies db/migrations against DATABASE_URL
task test:integration     # go test -tags=integration against the same DATABASE_URL
```

`.github/workflows/checks.yaml`'s `integration` job runs exactly that against a `postgres:18`
service container. The isolation test also creates (if missing) a `solobill_test_app` role on
that database, `NOSUPERUSER NOBYPASSRLS` with an obviously-fake, test-only password, and runs
every row-level-security assertion through it rather than through `DATABASE_URL`'s own role: a
Postgres superuser bypasses row level security regardless of `FORCE ROW LEVEL SECURITY`, so
asserting isolation through a superuser connection would prove nothing.

## Conflict zones

- A branch that touches `internal/storage/postgres/sqlcgen/models.go` rebases onto `main` and
  runs `task generate:sqlc` again. It never hand merges a conflict in generated code.
- A migration uses a version inside its issue's reserved range. The ranges are the table
  "Migration timestamp reservation" in `docs/concepts/solobill.md`.
- A feature adds its routes in its own `internal/httpapi/routes_<resource>.go`, its Vue routes
  in `web/src/router/routes/<feature>.ts` and its strings in
  `web/src/i18n/locales/{de,en}/<feature>.json`. It does not edit the index files.
- The full list is the section "Conflict zones" in `docs/concepts/solobill.md`.

## Deviations

- This repository uses the Elastic License 2.0 instead of the organisation's baseline
  Apache-2.0.
- The Elastic License 2.0 is source available, not open source.
- The reason: this tool has product potential, so a third party should not be able to
  offer it as a hosted service without the author's own agreement.
- `Dockerfile`'s web stage installs corepack through npm instead of `mise`: Node stopped
  distributing corepack from Node.js 25 onward (nodejs/node PR 57617), and there is no `mise`
  inside that image stage to install it another way.
- `.yamllint.yaml`'s line-length limit is 140, not the baseline's 120. A pinned action
  reference then fits on one line together with its version comment, matching
  most of the organisation's own repositories.
